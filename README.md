# MWI 试炼分配计算器 · 二次开发包

## 一、项目定位
银河奶牛（MWI，milkywayidle.com）公会「试炼分配计算器」。给定公会成员的技能等级与装备，用算法算出 4 个试炼最优人员分配，使公会总通关数最高。

纯 Excel 公式无法实现（核心分配算法是迭代图算法 MCMF + 局部搜索），故落地为独立单页 Web 工具。

## 二、本包结构（源码 + 资源，可直接二次开发）
```
mwi_devkit/
├── README.md
├── generate_html.py              # 从素材生成计算器网页（单文件 HTML）
├── items.svg                     # 装备图标源（960 个 SVG symbol）
├── skills_sprite.svg             # 17 个纯技能图标（来自游戏 CDN）
├── buffs_sprite.svg              # 全局 BUFF 图标（gathering/efficiency/action_speed，来自游戏 CDN）
├── guild_sprite.svg              # 公会建筑/神龛图标（23 建筑 + 5 神龛，来自游戏 misc_sprite）
├── house_sprite.svg              # 17 个房屋房间图标（house_*，来自游戏 misc_sprite）
├── equip.json                    # 权威槽位→中文装备名列表（生成 EQUIP_ICONS / EQUIP_FAMILIES 用；含「★」精炼款）
├── item_name_map.json            # 中文名→iconId 映射（生成图标用）
├── mwi_data.json                 # 游戏数据（装备加成表/房屋/成就/公会建筑/神龛，构建期内联）
└── mwi_data_export.user.js       # 油猴导出脚本（v0.9.0，源文件）
```
说明：
- `mwi_trial_calculator.html`（计算器成品）由 `generate_html.py` 生成，**不纳入本包**；用本包可随时重新生成，避免与源素材重复。
- `skill_icons.svg` 等中间产物均由 `items.svg` 派生，无需单独保留，生成方式已内置于 `generate_html.py`。
- `generate_html.py` 内的路径已扁平化：`equip.json`、`item_name_map.json` 直接从包根目录读取。

## 三、两大组件

### 1. 计算器网页（由 generate_html.py 生成的单文件 HTML）
- 单页布局：顶部 4 个试炼配置卡片（技能图标选择 + 人数上限显示 + 可滚动成员列表）→ 全局加成栏 → 公会建筑栏 → 下方成员大表格。
- **试炼「人数上限」不可手改**：由**公会生活营地等级**派生（对齐游戏客户端 `partyCapForKind`）：`上限 = 20 + min(生活营地等级, 20) × 2`；战斗试炼同理 `40 + min(战斗营地, 20) × 2`（暂未模拟战斗试炼）。卡片上显示数值 + 一行「由生活营地决定」提示，hover 显示算式。
- 双展示分配结果：成员表「分配」列显示试炼图标 + 试炼卡片下方滚动成员列表，两处同步。
- **个人装备系统（v6.8，三区）**：装备按「生活装备 / 生活 · 战斗两用 / 战斗装备 + 生活工具」分开管理，都随共享 payload 逐人上传。
  - **生活装备（拥有制，7 槽）**：`上衣`10 件 / `下装`10 件 / `披风`4 件按槽位分行；`头部 / 手部 / 脚部 / 副手` 各 1 件（红厨师帽 · 附魔手套 · 收藏家靴 · 掌上监工）合并为「单件」一行。同一槽位里有多个互不替代的物品（10 套技能套装 + 4 类披风），所以按「是否拥有」记录（`member.ownedEquip[slot][iconId] = 强化等级`，上限 +20）；推演时每个试炼技能从该槽位已勾选物品里取收益最高的一件（同一槽位只能穿一件 → 择优而不是累加）。判定用与推演同口径的产出速度，因此 `+15 挤奶工上衣` 会胜过同槽位的战斗护甲。
  - **方格 + 强化小面板（v6.8）**：每件装备是一个 **36×36 方格**（与工具 / 战斗装备同款，只有图标，物品名在悬停提示里）。**未拥有 = 虚线框 + 图标灰度**，已拥有 = 实线高亮 + 左上角标 `★ +N`（★ 在强化等级左边）。**点方格**弹出 `.enh-pop` 小面板设置强化等级（`− / 数字输入 / +`，+0~+20）与 `★ 精炼`，面板里可「取消拥有」；未拥有的方格点一下即以 `+0` 拥有并打开面板。
  - **披风精炼（★）**：4 类披风各含普通款与 ★ 精炼款，游戏里二者互斥 → 界面上是 **1 个方格 + 小面板里的 ★ 开关**（切换时保留强化等级）。数据上体现为 `ownedEquip['背部'][base]` 或 `ownedEquip['背部'][base + '_refined']` 二者之一；两者若同时存在，保留精炼款。
  - **生活工具 · 唯一一件（单选）**：10 个工具（挤奶…强化）有上下位替代（彩虹刷子 / 神圣刷子…），只记录当前使用的一件。
  - **生活 · 战斗两用 · 一槽一件（v6.7）**：`项链 / 耳环 / 戒指 / 袋子` 这 4 个槽位里既有生活件（效率项链、采集耳环…）也有战斗件（战士项链、暴击戒指…），而你只能穿一件 —— 与生活工具同款「配装选择器」，**每部位选一个**（存 `member.equipment[slot]`，不是勾选集合）。选择器不排除任何物品（生活/战斗都能选）。`袋子` 的所有型号在游戏里只提供食物 / 饮料槽位与生命 / 法力上限，对生活技能**恒为 0**。
  - **战斗装备 · 配装制（一槽一件）**：**8 个配装槽**：主手 / 副手 / 头部 / 身体 / **腿部 / 手部** / 脚部 / 背部（腿部与手部顺序按需求互换）；点击槽位打开 Enhancelator 风格图标网格选择器 + 强化等级 +0~+20。选择器会**排除已在生活装备区勾选的同槽位物品**（`头部/身体/手部/腿部/脚部/背部/副手` 的生活件），避免重复录入。
  - **精炼倍率**：官方 2025/8/20 调整后 —— 精炼装备 **+8%**，背部（披风）槽位的精炼装备 **+16%**；未精炼装备没有任何倍率加成。`itemStatTotals` 里即 `refined ? (背部 ? 1.16 : 1.08) : 1`。
  - 生活/战斗**互不争抢**：拥有制槽位有物品时，生活试炼只用拥有制里的；拥有集合为空才回落到配装槽（兼容旧数据）。旧版「一槽一件」的数据会自动迁移进拥有集合（仅当该物品属于该槽位可勾选的家族）；v6.6 曾把两用槽记进 `ownedEquip`，v6.7 起会自动取强化最高的一件搬回配装槽并清空（迁移幂等）。
  - 游戏 `profile_shared` 只含「当前穿戴」的 24 件、**不含背包**，因此导入只能把穿戴中、属于可勾选家族的装备作为拥有集合初值，其余拥有项需手工补勾。
- **全局 BUFF**：顶部「全局加成」栏三项输入——采集数量（gathering）/生产效率（efficiency）/强化速度（action_speed），0=无、1~20 级，加成% = 19.5 + 等级×0.5（Enhancelator 风格公式）。采集类→双倍产出概率、生产类→效率、强化→动作速度。仅本地保存（localStorage `mwi_global_buffs`），不上传共享。三项**横向单行**显示（自动换行）。
- **公会建筑**（**公会全局，随共享数据上传**）：对齐游戏 23 座（上限 20 级），按 **功能建筑 / 生活类建筑 / 战斗类建筑** 三块显示，**三块各占一行**；每块内部是 **每行最多 5 个的等宽网格**（页面变窄自动降到 4 / 3 / 2 个），等宽列让字数不同的建筑名（「公会奶牛棚」vs「公会奶酪锻造坊」）自动按最宽的那列对齐，等级输入框右对齐。key/中英名/图标/hrid 见 `mwi_data.json` 的 `guildBuilding`。
  - 6 座**功能建筑**（公会大厅/建造者殿堂/金库/档案馆/生活营地/战斗营地）：成员上限、公会点数、代币、经验、生活试炼参加人数 +2/级、战斗试炼参加人数 +2/级；**不影响试炼层数**，界面中以弱化样式标出（hover 有说明）。
  - 10 座**生活类建筑**（公会奶牛棚…公会天文台，对应 10 个生活技能）：仅在本公会试炼期间为成员提供加成，每级 **+2 有效等级**（近似值，游戏内实际效果由服务端下发）。
  - 7 座**战斗类建筑**（公会餐厅…公会神秘研究室，对应 7 个战斗属性）：同上，暂未参与战斗试炼模拟。
  - 建筑等级存在 `state.guildBuildings` + `state.guildBuildingsTs`，进入共享 payload（bin/localStorage）；合并时按时间戳取新（谁最后改以谁为准）。旧版 localStorage `mwi_guild_buildings` 会自动迁移一次。
- **成员详情弹窗（v6.4）**：成员的**全部个人数据** —— 专业等级(10) / 装备 / 房屋(17) / 神龛(10) / 成就(6) —— 都不再横排在主表里，改为点每行「详情」按钮弹出的编辑弹窗（复用 `.modal-overlay` / `.modal-dialog`，宽 920px）。弹窗内按固定顺序 **专业 → 装备 → 房屋 → 神龛 → 成就完成** 分区块网格排布、逐项可编辑，改动即随共享 payload 上传。主表因此只剩 **4 列**（分配 / 角色名 / 详情 / 删除）。
  - **分组网格（v6.7）**：`.detail-grid` 统一为**每行最多 5 个**的等宽网格（`repeat(5,minmax(0,1fr))`），并按视口宽度自动降到 4（≤1100px）/ 3（≤860px）/ 2（≤640px）—— 专业 10 项、生活工具 10 格、房屋 17 间等都按此排布；生活装备的方格行 `.own-chips` 是 **36px 定宽方格**（`repeat(5,36px)`，上装 / 下装各 10 件 → 各 2 行），定宽保证上下两行的图标对齐，且因为格子不随宽度伸缩，窄屏无需降列。
  - 专业等级区块：10 个技能（图标 + 名称 + 数字输入），改完只刷新弹窗。
  - 装备区块（v6.8）：再分**四个子区块** —— **生活装备**：按槽位分行，每件装备是一个 **36×36 方格**（只有图标，名字在悬停提示里；未拥有为虚线灰度，拥有后左上角标 `★ +N`）。**生活 · 战斗两用**：项链/耳环/戒指/袋子 各一个**配装单选格**。**生活工具（单选）** 10 格、**战斗装备（配装制）** 8 格（主手/副手/头部/身体/**腿部/手部**/脚部/背部），点击打开原装备选择器。
  - 强化等级小面板（v6.6 加、v6.7 修、v6.8 简化）：**点方格**弹出 `.enh-pop` 浮层（挂在 `body` 上、`position:fixed`，不会被弹窗滚动容器裁切），内含 `− / 数字输入 / +` 与 `★ 精炼` 开关、「取消拥有」「完成」；点浮层外部关闭。**实现要点**：① 「点外部关闭」的 document 监听要 `setTimeout(…, 0)` 延后一帧挂载（触发本次打开的那次 click 正在冒泡，立刻挂会在同一轮里把它关掉）；② 锚点 `getBoundingClientRect()` 必须在重绘之前取（点未拥有方格会先「顺手拥有」并重绘，之后锚点已脱树、rect 全归零）。缺任何一条都会表现为「点了没反应」或「面板闪一下就没 / 跑到左上角」。
  - 神龛区块：**分两行** —— 上行「生活类」5 座、下行「战斗类」5 座（每行 5 列等宽网格），项标签只保留神龛本名（力量/节奏/精神/稀有/学者），生活/战斗由行首标签表达。
- **个人神龛（5 座 × 生活/战斗 = 10 槽）—— 没有全局输入框**：神龛等级属于**个人属性**，在详情弹窗「神龛」区块（生活/战斗两行）编辑，随共享 payload 逐人同步。上限 20 级。
  - 每座神龛拆成 **`xx神龛（生活）`** 与 **`xx神龛（战斗）`** 两个槽位（数据键 `member.shrines[<shrine>_skilling]` / `[<shrine>_combat]`）。
  - 数值取自游戏 `guildBuffDetailMap`（权威）：**生活** force=效率 +0.5%/级、tempo=动作速度 +0.5%/级、spirit=精华掉率 +2%/级、rarity=稀有掉率 +1%/级、scholar=智慧 +0.5%/级；**战斗** force=伤害 +0.3%/级、tempo=攻击/施法速度 +0.4%/级、spirit=生命/法力上限 +1%/级、rarity=稀有掉率 +1%/级、scholar=智慧 +0.5%/级。
  - **只有 生活版 力量/节奏 影响生活试炼推演**（效率/动作速度）；其余 8 项置灰并注明「不影响试炼层数 / 仅影响战斗试炼（暂未模拟）」。战斗变体的数值由 `computeCombatBonuses()` 聚合成伤害/攻速/施法速度/生命法力上限等，为后续战斗试炼预留。
  - 导入成员数据时按 `guildBuffLevelMap` 的 `buffHrid` 逐槽位填充（样例中 `force_skilling=2` 与 `force_combat=4` 确实是两个不同的值）。**角色名后不再显示神龛等级徽标**。
- **成就档位（个人持久化数据，6 项）**：详情弹窗「成就完成」区块 6 个勾选框（**初学者 / 新手 / 熟练者 / 老手 / 精英 / 冠军**，名称下方小字是该档加成的技能），与技能/装备/神龛一样属于**每个成员的状态**，随共享 payload 逐人上传（`member.achievements`，按 `_ts` 合并）。
  - 加成为「该档全部成就完成」才解锁，数值取自游戏 `achievementTierDetailMap`：初学者=采集数量 +2%、新手=经验 +2%、熟练者=效率 +2%、老手=稀有发现 +2%、**精英=伤害 +2%（战斗向）**、冠军=强化成功率 +0.2%。
  - 影响生活试炼推演的是 初学者 / 熟练者 / 冠军；**不影响推演的 新手(经验) / 老手(稀有发现) / 精英(伤害) 三项置灰**（精英另进 `computeCombatBonuses()`，为后续战斗试炼预留）。
  - 导入时从 profile 的 `achievementsValue` 或 `characterAchievements`（数组，`[{achievementHrid,isCompleted}]`）归一化后物化成勾选状态；勾选后即为算法权威值。原始成就全表**不落库**（避免 80 人 × 上百条撑大共享载荷，免费 bin 单条上限 100KB）。
- **房屋房间（个人持久化数据，17 项）**：详情弹窗「房屋」区块 10 个**生活房间** + 7 个**战斗房间**（图标 + 名称 + 数字输入），随共享 payload 逐人上传（`member.houseRooms`）。上限 20 级。
  - 加成为房间等级 × 每级增益，取自游戏 `houseRoomDetailMap`：奶牛棚/花园/木棚/锻造台/工作间/缝纫室/厨房/冲泡坊/实验室 = 对应技能**效率 +1.5%/级**；天文台 = 强化**动作速度 +1%/级 + 强化成功率 +0.05%/级**。
  - 7 个战斗房间（射箭场/军械库/餐厅/道场/健身房/图书馆/神秘研究室）分别加 远程/防御/耐力/攻击/近战/智力/魔法 等级或攻速，置灰标注「仅影响战斗试炼（暂未模拟）」，进 `computeCombatBonuses()`。
  - 所有房间另有全局 +0.5%/级 经验、+0.2%/级 稀有掉率（不影响推演指标）。
  - 导入时从 profile 的 `characterHouseRoomMap`（`{"/house_rooms/x": {level}}`）物化；旧字段 `houseRoomLevels` / `houseActionTypeBuffsDict` 仍兼容。
- 图标：内联 **492** 个 SVG（17 技能 + 427 装备 + 3 全局 BUFF + 23 公会建筑 + 5 神龛 + **17 房屋**），来自 `skills_sprite.svg`、`items.svg`、`buffs_sprite.svg`、`guild_sprite.svg`、`house_sprite.svg`；装备图标经 `equip.json` + `item_name_map.json` 映射生成，无后缀猜测。
- 成员表列数 **4**：分配 1 + 角色名 1 + 详情 1 + 删除 1；专业 10 + 装备 **28 个生活装备方格** + **22 个配装选择器**（10 生活工具 + 8 战斗配装槽 + 4 两用槽）+ 房屋 17 + 神龛 10 + 成就 6 共 **全部在详情弹窗内**（弹窗区块顺序：专业 → 装备 → 房屋 → 神龛 → 成就完成）。
- **导出 / 导入（v6.9）**：顶部工具栏在「导入」右侧新增 **「导出」** 按钮 —— 把当前**全部数据**（`sharedPayload()`：成员 / 试炼 / 公会建筑 / 公会名，另含 `deletedIds` 墓碑）导出成一份 JSON 备份，文件名 `MWI试炼_<公会>_<N>人_<日期>.json`。可当**本地备份**或**换机器/换浏览器迁移**用。
  - 备份带 `_format:'mwi-trial-calculator'` 标记，用「导入」按钮即可**原样还原**：成员 id 重排、`applyTrialCaps()` 按营地重算人数上限、逐成员 `normalizeMemberEquip()` 归一化（未拥有/精炼互斥等约束照旧），端到端推演结果不变。
  - 导入**自动识别两种 JSON**：① **本计算器的备份**（含 `_format` 标记；也接受形如 `sharedPayload` 的裸对象 —— 方便把共享 bin 里的载荷直接拷出来导入）→ 整体还原；② **游戏导出的成员 profile 数组**（油猴脚本产物）→ 走原有「解析成成员列表」路径。两者都不是则提示「无法识别的 JSON」。
  - 备份里的**公会名只在本地还没有时采用**，避免导入别人的备份时把当前共享空间的公会名改掉。
  - 共享模式下导入后立即 `forcePushToBin` 全量覆盖 bin（与成员数组导入一致，不走合并）。
- i18n：中/英（`t(key)`，localStorage 持久化）。
- 主题：浅色/深色 CSS 变量切换。
- 算法常量：试炼 3600 秒、起始 100 级、每通关 +10 级；基础行动 10 秒、成功率 80%；每级基础 40000 点、每通关 +4000；人数膨胀系数 0.01。
- 核心算法 4 步：每人每技能指标 → 通关层数模拟（computePasses）→ 最小费用流分配（MCMF+SPFA）→ 局部搜索优化（localSearch，交换爬山）。

### 2. 数据导出油猴脚本 `mwi_data_export.user.js` v0.9.0
- 进游戏后 Hook WebSocket 抓取 `init_character_data` / `profile_shared` / `guild_buffs_updated` / `guild_updated`，缓存成员完整 profile。
- **采集对所有成员一视同仁，包括自己**：不做任何「自己角色」的特殊处理，也不依赖缓存跳过——每次采集都对名单里的人重新发 `view_profile` 并覆盖旧数据（用 `captures` 计数判断「又采到一个」，因为重采时 `Map.size` 不会增长）。
- **个人神龛增益**、**成就信息**都随原始 profile 一起导出（`guildBuffLevelMap` / `characterAchievements`）。
- **公会建筑等级**：`guild_updated` 的 `guildBuildingLevelMap`（键 `/guild_buildings/<building>`，公会全局），以 `_guildBuildingLevelMap` 挂在**第一位成员**上；计算器导入时自动预填建筑栏。
- **单按钮流程（v0.9.0）**：页面上**只有一个按钮**，且**只在「公会 - 成员」界面显示**（`MutationObserver` 跟踪 `[class*="GuildPanel_membersTable"]` 的出现/消失）。点「开始采集公会成员」→ 逐个 `view_profile`（经 WebSocket 直发，绕开 UI 可信校验）→ **采集完成自动导出 JSON**，不再有「重新采集」「点击导出」两个分开的按钮。
- 按钮状态机：`开始采集公会成员` → `采集中 x/y`（采集中禁用）→ `已导出 N 人 · 点此重采` / `采集失败 · 点此重试`。
- **待机时不再显示「已缓存 N 人」**：旧版在任何 WS 消息（含 `init_character_data`）到达时都会刷出「已缓存 N 人，点击导出」，而这里的 N 还含一个**尚未被采集过的「自己」**（`size + 1`），很容易让人误以为已经采完。现在按钮文案只由采集流程与显隐逻辑驱动。
- 输出 JSON 数组 = 本次采集到的全部 profile（含自己），文件名 `MWI_公会_N人_日期.json`。仅当一个成员都没采到时，才退回用实时 WS 数据重建自己那份（保留「只导出自己」的用法）。
- 油猴菜单命令 2 条：**「采集公会成员并保存 JSON」**（等价于点按钮）与「导出 JSON（当前已采集数据）」（手动兜底，只导出已采集到的内容）。

## 四、数据流（端到端）
1. 安装 `mwi_data_export.user.js` → 进游戏 → 切到公会 **成员** 页 → 页面右下角出现「开始采集公会成员」→ 点一下，采集完**自动下载** JSON。
2. 打开生成的计算器 HTML → 点「导入」读 JSON → 自动计算并显示分配。（导入同时接受计算器自己「导出」的备份）
3. 网页「导出」按钮可把当前全部数据存成备份 JSON；导入按钮旁有 📦 链接，可直接下载该油猴脚本（链接目标即 `mwi_data_export.user.js`）。

## 五、在线协作（jsonbin.io + 本地加密）
- 后端用 jsonbin.io public bin：创建须带 `X-Bin-Private:false`；写操作须带 `X-Master-Key`。
- **密钥派生**：加密密码为固定常量 `SHARE_PASSWORD = 'layu'`，`PBKDF2('layu', guild)` 派生 AES-GCM 256 密钥（兼容既有 bin）。分享链接只含 `guild` + `bin` 两个参数，不再带 `pwd`/`mk`（旧链接的 `mk` 参数仍向后兼容读取）。
- Master Key 只存创建者本地（localStorage），不进分享链接——写权限真正受控于创建者。
- gzip 压缩：免费套餐单条 100KB 上限，80 人数据经 gzip 后约 5.9KB base64；用 CompressionStream/DecompressionStream，不支持时降级不压缩。
- **导入语义**：导入 JSON = 整体替换名单，导入成员统一打 `_ts` 并立即 `forcePushToBin` 全量覆盖 bin（不走合并），防止被远端旧数据覆盖。导入**同时接受两种格式**：计算器「导出」的备份（`_format` 标记，或形如 `sharedPayload` 的裸对象）与游戏导出的成员 profile 数组。
- **删除语义（墓碑机制）**：`deletedIds` 记录已删除成员 id，`mergeState` 合并两端墓碑并过滤，防止共享模式下删除的成员被远端旧数据"复活"。
- 并发安全：保存时先 GET 远端，按 `_ts` 时间戳逐条合并（merge-on-save）。共享模式显示 🔄 刷新按钮。
- 无 URL 参数时走 localStorage 离线模式。
