# MWI 试炼分配计算器 · 二次开发包

## 一、项目定位
银河奶牛（MWI，milkywayidle.com）公会「试炼分配计算器」。给定公会成员的技能等级与装备，用算法算出 4 场生活试炼的最优人员分配，使公会奖励的基础点数总和最大。

纯 Excel 公式无法实现（核心分配算法是迭代图算法 MCMF + 局部搜索），故落地为独立单页 Web 工具。

说明：
- `mwi_trial_calculator.html`（计算器成品）由 `generate_html.py` 生成，**不纳入本包**；用本包可随时重新生成，避免与源素材重复。
- CSS / JS / HTML 在 `src/` 下独立维护：`generate_html.py` 只负责读取它们、注入游戏数据与 SVG symbol、替换占位符，产物仍是单文件。改样式改 `src/styles.css`，改逻辑改 `src/app.js`；直接改产物会被下次构建覆盖。
- `src/app.js` 里的三行数据占位注释（`// __EQUIP_ICONS_PLACEHOLDER__`、`// __LIFE_EQUIP_PLACEHOLDER__`、`// __GAME_DATA_PLACEHOLDER__`）是构建注入点，不要删除。
- `skill_icons.svg` 等中间产物均由 `items.svg` 派生，无需单独保留，生成方式内置于 `generate_html.py`。
- `generate_html.py` 从 `assets/` 读取 `equip.json`、`item_name_map.json`、`equip_levels.json` 及各 SVG。
- `equip_levels.json` 由游戏 `init_client_data` 的 `itemDetailMap` 提取（`itemLevel` 字段，键为 iconId 去掉 `/items/` 前缀），共 886 项；基础款与「★」精炼款等级相同。构建期内联为 `const EQUIP_LEVELS`；导入配装时同槽位多件互斥按它比较——**等级高者覆盖等级低者**；等级相同/任一方无数据则保留本地。

## 三、两大组件

### 1. 计算器网页（由 generate_html.py 生成的单文件 HTML）
- 单页布局：顶部 4 个试炼配置卡片（技能图标选择 + 人数上限显示 + 可滚动成员列表）→ 全局加成栏 → 公会建筑栏 → 下方成员大表格。
- **试炼「人数上限」不可手改**：由**公会生活营地等级**派生（对齐游戏客户端 `partyCapForKind`）：`上限 = 20 + min(生活营地等级, 20) × 2`；战斗试炼同理 `40 + min(战斗营地, 20) × 2`（暂未模拟战斗试炼）。卡片上显示数值 + 一行「由生活营地决定」提示，hover 显示算式。
- 双展示分配结果：成员表「分配」列显示试炼图标 + 试炼卡片下方滚动成员列表，两处同步。
- **个人装备系统（三区）**：装备按「生活装备 / 生活 · 战斗两用 / 战斗装备 + 生活工具」分开管理，都随共享 payload 逐人上传。
  - **生活装备（拥有制，7 槽）**：`上衣`10 件 / `下装`10 件 / `披风`4 件按槽位分行；`头部 / 手部 / 脚部 / 副手` 各 1 件（红厨师帽 · 附魔手套 · 收藏家靴 · 掌上监工）合并为「单件」一行。同一槽位里有多个互不替代的物品（10 套技能套装 + 4 类披风），所以按「是否拥有」记录（`member.ownedEquip[slot][iconId] = 强化等级`，上限 +20）；推演时每个试炼技能从该槽位已勾选物品里取收益最高的一件（同一槽位只能穿一件 → 择优而不是累加）。判定用与推演同口径的产出速度，因此 `+15 挤奶工上衣` 会胜过同槽位的战斗护甲。
  - **方格 + 强化小面板**：每件装备是一个 **36×36 方格**（与工具 / 战斗装备同款，只有图标，物品名在悬停提示里）。**未拥有 = 虚线框 + 图标灰度**，已拥有 = 实线高亮 + 左上角标 `★ +N`（★ 在强化等级左边）。**点方格**弹出 `.enh-pop` 小面板设置强化等级（`− / 数字输入 / +`，+0~+20）与 `★ 精炼`，面板里可「取消拥有」；未拥有的方格点一下即以 `+0` 拥有并打开面板。
  - **披风精炼（★）**：4 类披风各含普通款与 ★ 精炼款，游戏里二者互斥 → 界面上是 **1 个方格 + 小面板里的 ★ 开关**（切换时保留强化等级）。数据上体现为 `ownedEquip['背部'][base]` 或 `ownedEquip['背部'][base + '_refined']` 二者之一；两者若同时存在，保留精炼款。
  - **生活工具 · 唯一一件（单选）**：10 个工具（挤奶…强化）有上下位替代（彩虹刷子 / 神圣刷子…），只记录当前使用的一件。
  - **生活 · 战斗两用 · 一槽一件**：`项链 / 耳环 / 戒指 / 袋子` 这 4 个槽位里既有生活件（效率项链、采集耳环…）也有战斗件（战士项链、暴击戒指…），而你只能穿一件 —— 与生活工具同款「配装选择器」，**每部位选一个**（存 `member.equipment[slot]`，不是勾选集合）。选择器不排除任何物品（生活/战斗都能选）。`袋子` 的所有型号在游戏里只提供食物 / 饮料槽位与生命 / 法力上限，对生活技能**恒为 0**。
  - **战斗装备 · 配装制（一槽一件）**：**8 个配装槽**：主手 / 副手 / 头部 / 身体 / **腿部 / 手部** / 脚部 / 背部（腿部与手部顺序按需求互换）；点击槽位打开 Enhancelator 风格图标网格选择器 + 强化等级 +0~+20。选择器会**排除已在生活装备区勾选的同槽位物品**（`头部/身体/手部/腿部/脚部/背部/副手` 的生活件），避免重复录入。
  - **精炼倍率**：精炼装备 **+8%**，背部（披风）槽位的精炼装备 **+16%**；未精炼装备没有任何倍率加成。`itemStatTotals` 里即 `refined ? (背部 ? 1.16 : 1.08) : 1`。
  - 生活/战斗**互不争抢**：拥有制槽位有物品时，生活试炼只用拥有制里的；拥有集合为空才回落到配装槽。`ownedEquip` 中的两用槽物品在 `normalizeMemberEquip()` 归一化时取强化最高的一件搬回配装槽并清空（幂等）。
  - 游戏 `profile_shared` 只含「当前穿戴」的 24 件、**不含背包**，因此导入只能把穿戴中、属于可勾选家族的装备作为拥有集合初值，其余拥有项需手工补勾。
- **全局 BUFF**：顶部「全局加成」栏三项输入——采集数量（gathering）/生产效率（efficiency）/强化速度（action_speed），0=无、1~20 级，加成% = 19.5 + 等级×0.5（Enhancelator 风格公式）。采集类→双倍产出概率、生产类→效率、强化→动作速度。仅本地保存（localStorage `mwi_global_buffs`），不上传共享。三项**横向单行**显示（自动换行）。
- **公会建筑**（**公会全局，随共享数据上传**）：对齐游戏 23 座（上限 20 级），按 **功能建筑 / 生活类建筑 / 战斗类建筑** 三块显示，**三块各占一行**；每块内部是 **每行最多 5 个的等宽网格**（页面变窄自动降到 4 / 3 / 2 个），等宽列让字数不同的建筑名（「公会奶牛棚」vs「公会奶酪锻造坊」）自动按最宽的那列对齐，等级输入框右对齐。key/中英名/图标/hrid 见 `mwi_data.json` 的 `guildBuilding`。
  - 6 座**功能建筑**（公会大厅/建造者殿堂/金库/档案馆/生活营地/战斗营地）：成员上限、公会点数、代币、经验、生活试炼参加人数 +2/级、战斗试炼参加人数 +2/级；**不影响试炼层数**，界面中以弱化样式标出（hover 有说明）。
  - 10 座**生活类建筑**（公会奶牛棚…公会天文台，对应 10 个生活技能）：仅在本公会试炼期间为成员提供加成，每级 **+2 有效等级**（近似值，游戏内实际效果由服务端下发）。
  - 7 座**战斗类建筑**（公会餐厅…公会神秘研究室，对应 7 个战斗属性）：同上，暂未参与战斗试炼模拟。
  - 建筑等级存在 `state.guildBuildings` + `state.guildBuildingsTs`，进入共享 payload（bin/localStorage）；合并时按时间戳取新（谁最后改以谁为准）。初始化时也会读取 localStorage `mwi_guild_buildings` 并迁移一次。
- **成员详情弹窗**：成员的**全部个人数据** —— 专业等级(10) / 装备 / 房屋(17) / 神龛(10) / 成就(6) —— 都在点每行「详情」按钮弹出的编辑弹窗内（复用 `.modal-overlay` / `.modal-dialog`，宽 920px）。弹窗内按固定顺序 **专业 → 装备 → 房屋 → 神龛 → 成就完成** 分区块网格排布、逐项可编辑，编辑后即随共享 payload 上传。主表共 **6 列**（分配 / 角色名 / 主力专业 / 主手 / 详情 / 删除），其中两列速览为纯展示，编辑入口只有详情弹窗。
  - **分组网格**：`.detail-grid` 统一为**每行最多 5 个**的等宽网格（`repeat(5,minmax(0,1fr))`），并按视口宽度自动降到 4（≤1100px）/ 3（≤860px）/ 2（≤640px）—— 专业 10 项、生活工具 10 格、房屋 17 间等都按此排布；生活装备的方格行 `.own-chips` 是 **36px 定宽方格**（`repeat(5,36px)`，上装 / 下装各 10 件 → 各 2 行），定宽保证上下两行的图标对齐，且因为格子不随宽度伸缩，窄屏无需降列。
  - 专业等级区块：10 个技能（图标 + 名称 + 数字输入），改完只刷新弹窗。
  - 装备区块：再分**四个子区块** —— **生活装备**：按槽位分行，每件装备是一个 **36×36 方格**（只有图标，名字在悬停提示里；未拥有为虚线灰度，拥有后左上角标 `★ +N`）。**生活 · 战斗两用**：项链/耳环/戒指/袋子 各一个**配装单选格**。**生活工具（单选）** 10 格、**战斗装备（配装制）** 8 格（主手/副手/头部/身体/**腿部/手部**/脚部/背部），点击打开原装备选择器。
  - 强化等级小面板：**点方格**弹出 `.enh-pop` 浮层（挂在 `body` 上、`position:fixed`，不会被弹窗滚动容器裁切），内含 `− / 数字输入 / +` 与 `★ 精炼` 开关、「取消拥有」「完成」；点浮层外部关闭。**实现要点**：① 「点外部关闭」的 document 监听要 `setTimeout(…, 0)` 延后一帧挂载（触发本次打开的那次 click 正在冒泡，立刻挂会在同一轮里把它关掉）；② 锚点 `getBoundingClientRect()` 必须在重绘之前取（点未拥有方格会先「顺手拥有」并重绘，之后锚点已脱树、rect 全归零）。缺任何一条都会表现为「点了没反应」或「面板闪一下就没 / 跑到左上角」。
  - 神龛区块：**分两行** —— 上行「生活类」5 座、下行「战斗类」5 座（每行 5 列等宽网格），项标签只保留神龛本名（力量/节奏/精神/稀有/学者），生活/战斗由行首标签表达。
- **个人神龛（5 座 × 生活/战斗 = 10 槽）—— 没有全局输入框**：神龛等级属于**个人属性**，在详情弹窗「神龛」区块（生活/战斗两行）编辑，随共享 payload 逐人同步。上限 20 级。
  - 每座神龛拆成 **`xx神龛（生活）`** 与 **`xx神龛（战斗）`** 两个槽位（数据键 `member.shrines[<shrine>_skilling]` / `[<shrine>_combat]`）。
  - 数值取自游戏 `guildBuffDetailMap`（权威）：**生活** force=效率 +0.5%/级、tempo=动作速度 +0.5%/级、spirit=精华掉率 +2%/级、rarity=稀有掉率 +1%/级、scholar=智慧 +0.5%/级；**战斗** force=伤害 +0.3%/级、tempo=攻击/施法速度 +0.4%/级、spirit=生命/法力上限 +1%/级、rarity=稀有掉率 +1%/级、scholar=智慧 +0.5%/级。
  - **只有 生活版 力量/节奏 影响生活试炼推演**（效率/动作速度）；其余 8 项置灰并注明「不影响试炼层数 / 仅影响战斗试炼（暂未模拟）」。战斗变体的数值由 `computeCombatBonuses()` 聚合成伤害/攻速/施法速度/生命法力上限等，为后续战斗试炼预留。
  - 导入成员数据时按 `guildBuffLevelMap` 的 `buffHrid` 逐槽位填充（样例中 `force_skilling=2` 与 `force_combat=4` 确实是两个不同的值）。
- **成就档位（个人持久化数据，6 项）**：详情弹窗「成就完成」区块 6 个勾选框（**初学者 / 新手 / 熟练者 / 老手 / 精英 / 冠军**，名称下方小字是该档加成的技能），与技能/装备/神龛一样属于**每个成员的状态**，随共享 payload 逐人上传（`member.achievements`，按 `_ts` 合并）。
  - 加成为「该档全部成就完成」才解锁，数值取自游戏 `achievementTierDetailMap`：初学者=采集数量 +2%、新手=经验 +2%、熟练者=效率 +2%、老手=稀有发现 +2%、**精英=伤害 +2%（战斗向）**、冠军=强化成功率 +0.2%。
  - 影响生活试炼推演的是 初学者 / 熟练者 / 冠军；**不影响推演的 新手(经验) / 老手(稀有发现) / 精英(伤害) 三项置灰**（精英另进 `computeCombatBonuses()`，为后续战斗试炼预留）。
  - 导入时从 profile 的 `achievementsValue` 或 `characterAchievements`（数组，`[{achievementHrid,isCompleted}]`）归一化后物化成勾选状态；勾选后即为算法权威值。原始成就全表**不落库**（避免 80 人 × 上百条撑大共享载荷，免费 bin 单条上限 100KB）。
- **房屋房间（个人持久化数据，17 项）**：详情弹窗「房屋」区块 10 个**生活房间** + 7 个**战斗房间**（图标 + 名称 + 数字输入），随共享 payload 逐人上传（`member.houseRooms`）。上限 20 级。
  - 加成为房间等级 × 每级增益，取自游戏 `houseRoomDetailMap`：奶牛棚/花园/木棚/锻造台/工作间/缝纫室/厨房/冲泡坊/实验室 = 对应技能**效率 +1.5%/级**；天文台 = 强化**动作速度 +1%/级 + 强化成功率 +0.05%/级**。
  - 7 个战斗房间（射箭场/军械库/餐厅/道场/健身房/图书馆/神秘研究室）分别加 远程/防御/耐力/攻击/近战/智力/魔法 等级或攻速，置灰标注「仅影响战斗试炼（暂未模拟）」，进 `computeCombatBonuses()`。
  - 所有房间另有全局 +0.5%/级 经验、+0.2%/级 稀有掉率（不影响推演指标）。
  - 导入时从 profile 的 `characterHouseRoomMap`（`{"/house_rooms/x": {level}}`）物化；同时兼容 `houseRoomLevels` / `houseActionTypeBuffsDict` 字段。
- 图标：内联 **492** 个 SVG（17 技能 + 427 装备 + 3 全局 BUFF + 23 公会建筑 + 5 神龛 + **17 房屋**），来自 `assets/` 下的 `skills_sprite.svg`、`items.svg`、`buffs_sprite.svg`、`guild_sprite.svg`、`house_sprite.svg`；装备图标经 `equip.json` + `item_name_map.json` 映射生成，无后缀猜测。
- 成员表列数 **6**：分配 1 + 角色名 1 + **主力专业 1** + **主手 1** + 详情 1 + 删除 1；专业 10 + 装备 **28 个生活装备方格** + **22 个配装选择器**（10 生活工具 + 8 战斗配装槽 + 4 两用槽）+ 房屋 17 + 神龛 10 + 成就 6 共 **全部在详情弹窗内**（弹窗区块顺序：专业 → 装备 → 房屋 → 神龛 → 成就完成）。
- **成员表两列速览**：主表空旷时一眼看清「这个人强在哪、带什么家伙」。
  - **主力专业**：该成员**等级最高的 3 个专业**（等级 0 不列出、全 0 显示 `-`），每项 = **技能图标 + 等级 + 该专业当前使用的工具图标**（无工具时显示虚线空心框）；名称与强化等级放 tooltip。等级相同时按技能顺序稳定排序；技能 → 工具槽位由 `SKILL_TOOL_SLOT`（`TOOL_SKILL_MAP` 反查）得到。
  - **主手**：主手战斗武器图标 + 强化角标 `+N`（未选择显示 `-`），tooltip 给名称与强化等级。
  - 两列都是**纯展示**（不新增交互、不参与推演），数据直接读 `member.levels` / `member.equipment`；新增成员（全 0 等级 + 空装备）自然显示 `-`。
- **导出 / 导入**：顶部工具栏在「导入」右侧有 **「导出」** 按钮 —— 把当前**全部数据**（`sharedPayload()`：成员 / 试炼 / 公会建筑 / 公会名，另含 `deletedIds` 墓碑）导出成一份 JSON 备份，文件名 `MWI试炼_<公会>_<N>人_<日期>.json`。可当**本地备份**或**换机器/换浏览器迁移**用。
  - 备份带 `_format:'mwi-trial-calculator'` 标记，用「导入」按钮即可还原（成员按角色名并集合并）：`applyTrialCaps()` 按营地重算人数上限、逐成员 `normalizeMemberEquip()` 归一化（未拥有/精炼互斥等约束照旧）。
  - 导入**自动识别两种 JSON**：① **本计算器的备份**（含 `_format` 标记；也接受形如 `sharedPayload` 的裸对象 —— 方便把共享 bin 里的载荷直接拷出来导入）→ 还原试炼/建筑/公会名，成员并集合并；② **游戏导出的成员 profile 数组**（油猴脚本产物）→ 走「解析成成员列表」路径。两者都不是则提示「无法识别的 JSON」。
  - 备份里的**公会名只在本地还没有时采用**，避免导入别人的备份时把当前共享空间的公会名改掉。
  - 共享模式下导入后立即 `forcePushToBin` 全量覆盖 bin（与成员数组导入一致，不走合并）。
  - 导入完成后弹出**导入报告**（精简版）：更新 / 新增 / 保留 各一行，新增与**保留**列出具体名单（更新只报数量，无解释文案）。**保留名单可就地删除**：悬停名字整体变红色删除按钮（+ ✕）→ 点一下变「确认删除?」→ 再点一下才真删（加墓碑 `deletedIds`、立即全量覆盖 bin、后台重算并刷新报告内名单与数量）；鼠标移开取消确认态。
- 试炼结果：每场试炼卡给出代币 / 最终比例 / 时间估算四行文本与**逐阶段通关耗时表**（行数 = 通关次数 + 1，表头固定在滚动区外，超时行变灰）；目标等级可配置（默认 100）；未分配成员名单为可滚动窗口，与试炼卡片同一行。
- 成员详情「生活属性」悬停按技能裁剪来源：房屋只列效率与强化的速度 / 成功率，公会建筑只列等级，全局 BUFF 只列实际生效的技能；成功率加成行只有强化显示，目标等级取配置值。
- i18n：中/英（`t(key)`，localStorage 持久化）。
- 主题：浅色/深色 CSS 变量切换；主题按钮图标只随当前主题取值（浅色 🌙 / 深色 ☀️），带切换悬停提示。
- 算法常量：试炼 3600 秒、起始 100 级、每通关 +10 级；基础行动 10 秒、成功率 80%；每级基础 40000 点、每通关 +4000；人数膨胀系数 0.01。
- 核心算法：每人每技能指标 → 通关层数模拟（`computePasses` / `simulateTrialProgress`）→ 最小费用流初始分配（MCMF + SPFA，cost = `-expectedRate(m, START_LV)`）→ 局部搜索（`localSearch`，以 `tokenReward` 为目标：单成员移动含 `newT=-1` 踢出、贪心两两交换并带双端点速率剪枝）→ `pruneNegativeContributions()` 精确复核移除负贡献成员（移除后该区代币是否上升）。
- **奖励换算**（官方公式，规则存档见 `docs/milkywayidle-游戏指南.md` → 公会 →「公会点数与公会代币」；`docs/` 另存新闻、更新日志两标签页正文）：
  - 单场生活试炼基础点数 `tokenReward` = 首层 200 + 之后每层 100 + 未完成层「进度 × 该层奖励 ÷ 2」（数值口径对齐 Chen19970809/MWI_Trial_Calculator）。**基础点数总和 = Σ 4 场 `tokenReward`**，即分配算法的优化目标。
  - 获得公会点数 = 基础点数总和 × (1 + 建造者殿堂等级 × **2%/级**)；总代币 = 0.5 × 基础点数总和 × (1 + 金库等级 × 2%/级)，为每位符合条件成员的代币；报名至少一场试炼者额外 +50%。
  - 系数：建造者殿堂、金库均为 **2%/级**。两个常量 `GUILD_POINTS_BONUS_PER_LEVEL` / `GUILD_TOKEN_BONUS_PER_LEVEL` 可调。
  - **每场试炼卡片上的「点数」是游戏口径**（基础 × 建造者殿堂倍率，括号附基础值），可直接与游戏内「1,610 点」这类数字对照。
  - 工作量模型经 `workDone` 精确验证：(40000+4000×档) × (1+1%×人数) 与游戏实际消耗的比值 = 1.001（workDone 是**成功后**的有效工作量）。
  - **全局加成需手动填写**：服务器社区大厅的全局 BUFF（采集数量 / 生产效率 / 强化速度，各 19.5+0.5×等级%）不在 profile 里，模拟器不会自动获取，按自己服务器的实际等级填「全局加成」三个输入框。导入时生活类公会建筑的有效等级加成（挤奶+6 / 采摘+6 / 缝纫+6 / 强化+6 等；`/guild_buildings/dairy_barn` 等 hrid → skill key 映射由 `applyImportedGuildBuildings` 处理）也计入。模型假设试炼过程中等级/配装不变。
  - 汇总栏显示「获得公会点数 / 总代币 / 总最终等级…」，两个奖励数字与试炼卡的「代币」（该试炼基础点数）都有悬停公式说明，中英文同步。
  - 本计算器只模拟 4 场生活试炼；游戏每周另有 2 场战斗试炼（首层 400、之后每层 200）未计入。

### 2. 数据采集油猴脚本 `mwi_profile_export.user.js`

**三条链路、三个按钮、全部模拟真人点击，采完自动导出。**

| 按钮 | 在哪个页面 | 做什么 | 导出 |
|---|---|---|---|
| ① 采集成员资料 | 公会 - 成员 | 逐个点成员 → 点「资料」 | `MWI_成员资料_…json`（纯数组，含技能等级 + 当前穿戴 + 公会建筑） |
| ② 采集生活配装 | 公会 - 试炼 | 打开生活试炼 → 逐个点「查看配装」 | `MWI_生活试炼配装_…json`（`_format:mwi-skilling-loadouts`） |
| ③ 采集战斗配装 | 公会 - 试炼 | 打开战斗试炼 → 逐个点「查看配装」 | `MWI_战斗试炼配装_…json`（`_format:mwi-combat-loadouts`） |

- **采集方式**：模拟真人依次点成员、点游戏菜单里的按钮，游戏自己带正确的 id 和 kind 发请求；脚本只在 WebSocket 上只读地收 `profile_shared` / `loadout_shared`。
- **生活 / 战斗配装分流**：点「查看配装」前记下 `{name, kind}`，回包据此落到 `skillingLoadouts` / `combatLoadouts` 两个 Map。同一人报两类试炼各采一份、互不覆盖。`hasLoadout:false` 的人回空配装（0 槽），照样算采到。
- **数据流**：`资料` = `profile_shared`（当前穿戴 + 技能等级，算点数的基础）；`查看配装` = `loadout_shared`（报名时绑定的那套配装，生活 23 槽带工具 / 战斗 13 通用槽）。游戏报名 `sign_up_guild_trial` 带 `characterLoadoutId`，试炼真正生效的是 loadout。签名报名人次之和 = 应采配装份数。
- **计算器导入**：三份 JSON 依次导入即可，按角色名合并（顺序无关）——资料提供技能/当前装备；两份配装除了挂到 `skillingLoadout` / `combatLoadout` 留存，还会把其中的装备**合并进当前装备**：工具/战斗件/两用槽走配装制（一槽一件），同槽位按游戏**装备等级 itemLevel（`equip_levels.json`）保留高级的一件**（不是按强化等级；等级相同/无数据则保留本地）；生活件走拥有制（多件并存、按技能择优）取并集。绝不覆盖技能等级/神龛/房屋；只在某类试炼出现的人建占位成员（等级全 0，不参与生活计算）。导入配装后会立即重算结果。
- **防高频风控**：一次只跑一条链路；每次点击/请求间有 850ms 起、向上抖动的间隔，看到「请勿过快」红条会自动退避并等 3s；试炼之间另有冷却。面板**仅在公会页显示**，可拖拽、可收起；底部日志实时显示每人成功/失败。GM 菜单 4 条（三链路 + 清缓存）。
- 只算生活点数时，**最少只导「成员资料」一份即可**（技能等级 + 当前穿戴都在里面）；另两份是报名绑定的实际配装，导入后会补齐当前穿戴缺失的装备槽（同槽位保留装备等级更高的一件），并把报名配装留在详情里供对照。

### 3. 一键导入自己的数据：书签小工具

计算器右上角「导入我的数据」提供**零插件**的单人自助通道，适合让每个成员自己补装备，不必装油猴脚本：

- 点开「导入我的数据」对话框即**自动生成**一条 `javascript:` 链接（无需再点按钮），把「导入我的数据」链接拖进书签栏（书签名即为此文字）；也可复制后手动建书签。计算器网址内嵌在链接里。对话框内明确说明：**只读游戏内存、不发网络请求、不含自动化操作、不改游戏数据**，并注明**仅支持电脑浏览器**（手机浏览器不支持书签脚本）。
- 在**游戏角色页**（网址含 `game?characterId=`）点这个书签：它从 React fiber 里读出游戏实时 state —— 角色名、当前穿戴 + 背包全部库存、技能、房屋等级、神龛 buff（`characterGuildBuffDict`）、成就完成表（`characterAchievementMap`），gzip+base64 编码后打开计算器并在 URL 带 `#mwiBookmark=<payload>`。**只读 state，不向游戏发送任何 WebSocket 指令**（不会触发「找不到角色名称」等游戏报错）；读不到数据会直接给出明确提示。
- 计算器读到该 hash 即解压、合并进成员（与油猴脚本同一套 `mergeMembersFromProfiles`），导入后清掉 hash 防重复，并**直接打开该成员的详情页**（不弹批量导入报告）。背包战斗装的处理：**空缺的战斗部位**（当前没穿的主手/副手/头/身/腿/手/脚/背）会从背包里按装备等级（`itemLevel`）最高、同级按强化等级最高的一件自动补上，只填空缺不覆盖已穿戴；不额外记录其它库存件，也没有额外的拥有角标 / 选择器标记。择优复用与资料 / 配装导入相同的 `equipItemLevel` 装备等级数据。
- **跳回计算器**：计算器页面会给自己的标签命名为 `mwiCalculator`；书签用 `window.open(url, "mwiCalculator")` 复用已打开的计算器标签（只改 hash → `hashchange` 监听触发导入并聚焦）。浏览器可能限制从 HTTPS 页面跳转 `file://` 本地文件，**本地 file:// 测试可不跳转，以上线后的 HTTP/HTTPS 地址为准**。若 `window.open` 被拦截，书签退而把 payload 复制到剪贴板，可在对话框点「从剪贴板导入」。
- 依赖浏览器的 `CompressionStream`（无则降级不压缩）；游戏页无 CSP 限制，书签可执行。它只读游戏内存 state，不改游戏数据。

## 四、数据流（端到端）

1. 安装 `mwi_profile_export.user.js` → 进游戏。公会页浮动面板在右下角，三个按钮：
   - 切到公会 **成员** 页 → 点「① 采集成员资料」→ 逐个点「资料」→ 采完自动下载 `MWI_成员资料_…json`。
   - 切到公会 **试炼** 页 → 点「② 采集生活配装」→ 打开生活试炼、逐个点「查看配装」→ 自动下载生活配装 JSON。
   - 仍在 **试炼** 页 → 点「③ 采集战斗配装」→ 打开战斗试炼、逐个点「查看配装」→ 自动下载战斗配装 JSON。
   - 三条链路一次跑一条、中间隔几分钟降风控；每条采完自动导出，不需要单独的导出按钮。
2. 打开计算器 HTML → 点「导入」**依次读这三份 JSON**（按角色名合并、各挂各的字段互不覆盖）→ 自动计算并显示分配。只算生活点数时最少只导「成员资料」一份即可。（导入同时接受计算器自己「导出」的备份）
   - 只想算生活试炼点数时，最少只需「资料当前装备」那份（含技能等级 + 当前穿戴）；生活/战斗配装两份是报名绑定的实际配装，导入后会把装备并进当前装备（同槽位按装备等级保留高级的一件）、并留在详情里供对照。
3. 网页「导出」按钮可把当前全部数据存成备份 JSON。

## 五、在线协作（jsonbin.io public bin）
- 后端用 jsonbin.io public bin：创建须带 `X-Bin-Private:false`；公开 bin 读取无需 key，写入带 `X-Master-Key`（带错 key 会被拒）。分享链接只含 `guild` + `bin` 两个参数；`mk` 参数也支持读取。
- 数据**不加密**：云端记录统一为 gzip + base64 的 `{z}`。bin 本身公开，固定密码没有保密意义，代码不再使用 AES / PBKDF2 / 固定密码。
- Master Key 只存创建者本地（localStorage），不进分享链接——写权限真正受控于创建者。访客打开分享链接时没有 key，状态栏显示「只读（未配置 Master Key）」，也不会发起 PUT（避免公开 bin 堆版本）；需要写入时在「共享设置」填入 Master Key 并点「保存密钥」，或用「重试同步」立即重推一次。
- 云端读写都会检查 HTTP 状态并把失败原因（含响应体）明确弹窗告知；写入失败时数据仍存本地，但不会把「没写成功」误当成同步成功。
- gzip 压缩后用 base64 存 `{z}`，免费套餐单条 100KB 上限（按实际 PUT body 字节计）；用 CompressionStream/DecompressionStream，不支持时降级不压缩。
- 带 Master Key 写入时同时发 `X-Bin-Versioning: false`，避免公开 bin 每次更新都堆版本（上限 1000，满了会 403）。
- 共享载荷在写入前统一瘦身：游戏原始 `characterHouseRoomMap` / `guildBuffLevels` / `_guildBuildingLevelMap` 不落盘（已物化成 `houseRooms` / `shrines` / 全局 `guildBuildings`）；试炼配装只留姓名、动作类型与 `wearableItemMap` 的 `itemHrid` + `enhancementLevel`，丢弃 `hash`、时间戳、技能/消耗品/触发器等计算用不到的字段。旧缓存和旧 bin 读入时也会压缩，超限会给出明确提示。
- **导入语义（两路统一「并集合并」）**：
  - **计算器备份**（`_format:'mwi-trial-calculator'`，或形如 `sharedPayload` 的裸对象）→ 还原**试炼 / 公会建筑 / 公会名**；**成员按角色名并集合并**（本地成员 id 保持不变）——备份里有的更新/新增，本地独有的原样保留，备份里某人的空字段不会把本地配置清空。
  - **游戏导出的成员 profile 数组** → **按角色名合并**：同名成员**逐字段取并集** —— 专业等级取较大值（游戏里等级只增不减）、个人神龛 / 房屋取非 0 值、成就档位取并集、配装槽逐槽位「非空才覆盖」、**装备拥有集合取并集**（游戏 `profile_shared` 只含当前穿戴的 24 件、**没有背包**，手动勾的部分必须留住）；空字段（0 / `{}` / `[]`）一律**不覆盖本地**——导入一份「空配置」绝不会把已配置好的成员刷空；采集里没有的本地成员（手动加的 / 已退会的）**原样保留，一个都不删**；新名字追加到名单末尾，id 接在当前最大 id 之后。
  - 两种导入完成后都会弹出**导入报告**（精简版）：更新 / 新增 / 保留 各一行，新增与**保留**列出具体名单（更新只报数量，无解释文案）。**保留名单可就地删除**：悬停名字整体变红色删除按钮（+ ✕）→ 点一下变「确认删除?」→ 再点一下才真删（加墓碑 `deletedIds`、立即全量覆盖 bin、后台重算并刷新报告内名单与数量）；鼠标移开取消确认态。
  - 两步都会立即 `forcePushToBin` 全量覆盖 bin（不走合并），防止被远端旧数据覆盖。
- **删除语义（墓碑机制）**：`deletedIds` 记录已删除成员 id，`mergeState` 合并两端墓碑并过滤，防止共享模式下删除的成员被远端旧数据"复活"。
- 并发安全：保存时先 GET 远端，按 `_ts` 时间戳逐条合并（merge-on-save）。共享模式显示 🔄 刷新按钮。
- 无 URL 参数时走 localStorage 离线模式，数据固定存在 `mwi_trial_data_v2`。加载时清理其它 `mwi_trial_*` 键；`saveData()` 遇到配额不足会先清理再重试，仍失败则弹窗告警。

## 六、构建与二次开发

### 自动部署（GitHub Actions）
`.github/workflows/deploy.yml`：每次推送到 `master`/`main`（或手动 Run workflow），自动完成 **构建 → 校验 → 提交产物到站点仓库**：

```
push → python generate_html.py → 校验产物完整性/体积 → 克隆 si-e/si-e.github.io
     → 写 mwi/index.html + mwi/mwi_profile_export.user.js → commit & push（只改 mwi/）
```

- 产物地址：`https://si-e.github.io/mwi/`（入口 `mwi/index.html`）；采集脚本 `mwi_profile_export.user.js` 与页面相对引用保持一致。
- 只改动目标仓库的 `mwi/` 目录，站点其它文件原样保留；**产物无变化时不会产生空提交**；目标仓库有新提交时自动 `rebase` 重试（最多 3 次）。
- 构建前置校验：产物必须生成、体积 > 1MB、且不含 `__CSS__` / `__JS__` / `__SVG_SYMBOLS__` 残留占位符，否则 job 直接失败（不会把坏产物推上线）。

**一次性配置**：在 `si-e/mwi_devkit` → Settings → Secrets and variables → Actions 新建 Secret **`DEPLOY_TOKEN`**，值为一个对 `si-e.github.io` 有 **Contents: Read and write** 权限的 PAT（fine-grained PAT 只需勾这一个仓库的 Contents 读写；classic PAT 需 `repo` 权限）。缺这个 Secret 时 job 会以明确报错终止。

## 七、边界与已知限制
- 导入接受两类来源：**计算器备份** → 还原试炼/建筑/公会名，成员并集合并；**游戏采集 JSON**（成员资料 / 生活配装 / 战斗配装）→ 按角色名合并，装备按等级并入当前装备（见上「导入语义」）。导入后立即以全量覆盖的方式写回共享 bin。
- 装备录入方式：**28 个生活装备方格**（上衣10/下装10/披风4/单件4）+ **22 个配装选择器**（10 生活工具 + 4 两用槽 项链/耳环/戒指/袋子 + 8 战斗配装槽 主手/副手/头部/身体/腿部/手部/脚部/背部），无护符，双手并入主手；装备图标 427 个全部成功映射。
- 全局 BUFF 仅本地生效，不参与共享同步；**公会建筑 + 个人神龛(10 槽) + 成就(6 档) + 房屋房间(17) + 装备拥有集合（含精炼标记）均进入共享 payload**（建筑按时间戳合并，其余逐人按 `_ts` 合并）。
- 已知近似：未收录进「装备基础加成表」的非工具装备（多为战斗护甲/武器，以及游戏里那批低阶技能护甲）会给一个**通用微小生活加成近似**（`+L×0.002 速度 / +L×0.001 效率 / +L×0.1 等级`）。**袋子槽位已按游戏事实排除该近似**（袋子只给食物/饮料槽位与生命/法力上限，对生活技能恒为 0）。
- 公会建筑已对齐游戏 23 座（上限 20，分功能/生活/战斗三类）；神龛 5 座 × 生活/战斗 = 10 槽（上限 20，个人属性）；房屋 17 间（上限 20，个人属性）；图标全部为游戏原生图标。
- 只有 **生活版** 力量(效率)/节奏(动作速度) 影响生活试炼层数，且完全按成员「个人」读取（`member.shrines['force_skilling']` ← `guildBuffLevelMap['/guild_buffs/force_skilling']`），**没有全局神龛输入与兜底**。
- 试炼人数上限由营地等级派生，不可手改：`20 + min(生活营地, 20)×2`（战斗为 40 基准，暂未模拟）。
- 战斗向数据（战斗神龛、战斗房屋房间、战斗类公会建筑、精英成就）目前只做聚合（`computeCombatBonuses()`），不参与生活试炼推演，为后续战斗试炼预备。
- 共享数据统一 gzip + base64 存入单条 jsonbin 记录的 `{z}` 字段；写入前按上节规则删除已物化的原始表和配装冗余字段，以适配免费套餐 100KB 上限。
- 测试基线：80 人满装备约 33ms，总等级 810 / 通关 41 次；冒烟测试 **237/237 PASS**、导出脚本行为 **14/14 PASS**（样例断言为「数据驱动」：默认取 Downloads 里最新的一份导出，只校验结构与公式，期望值由样例自身等级反推）。
